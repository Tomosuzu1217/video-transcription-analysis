02

GitHubとFirebaseの基礎知識

GitHubとは何か

Wordに例えると：Wordの「変更履歴の記録」をはるかに高度にしたもの。誰が・いつ・どの行を・どう変更したかが全て記録され、過去の任意の時点に戻せる。複数人が同時に別々の箇所を編集し、後で1つに統合することも可能。社内での位置づけは「ソースコードの金庫」。

Firebaseとは何か

飲食店に例えると：Firebaseは「厨房設備・レジ・予約システム・配達インフラが全部セットになったレンタルキッチン」。自分で建物を建てなくても、すぐに料理（アプリ）を提供できる。核心はFirebaseプロジェクトはGoogle Cloudプロジェクトと同一だということ。課金もGoogle Cloudの仕組みで処理される。

非エンジニア向け：よく出てくる用語集

リポジトリ：1つのプロジェクトのコードを保管する「フォルダ」。
Organization：会社単位の「組織アカウント」。オフィスビルの管理会社のように、メンバーの出入りや部屋の鍵を一括管理。
ブランチ：コードの「並行世界」。本番用・開発用・機能追加用など、複数の作業を同時進行するために枝分かれさせたもの。
ブランチ保護：本番コードに変更を反映する前に、別の人のチェックを必ず通すルール。銀行の送金で「上長の承認印が必要」という仕組みと同じ。
プルリクエスト：コードの「変更申請書」。変更内容を一覧で見せて、レビュアーが承認するとマージ（統合）される。
CI/CD：Continuous Integration / Continuous Delivery。コードが変更されるたびに自動でテスト・検査・デプロイ（本番反映）を実行する仕組み。
SAML SSO：社員証1枚で全フロアに入れるのと同じ。社内ID基盤でGitHubにもログイン可能。
SCIM：人事部が退職届を処理すると各システムの鍵が自動回収される状態。
IAM：「誰が・何に・どこまでアクセスできるか」の権限管理。フロアごとに入室できる社員を設定するのと同じ。
二要素認証（2FA）：マンションのオートロック＋部屋の鍵の二重ロック。
環境変数：コードの外にある「メモ書き」。パスワードやAPIキー等の秘密情報を、コード自体には書かずに外部から渡す仕組み。
.gitignore：「このファイルはGitHubにアップロードしないで」というルールを書いた設定ファイル。

Gitの基本概念：図解で理解する

GitとGitHubは別物

まず最も重要な区別から。Gitはソースコードの変更履歴を管理する「仕組み」そのもの。GitHubはGitで管理されたコードをインターネット上に保管し、チームで共有するための「サービス」だ。

Wordに例えると：Git＝「変更履歴の記録」という機能そのもの。GitHub＝「変更履歴つきのWordファイルをOneDriveに保管して、チームで共有する」こと。Gitはパソコン上で動く道具、GitHubはその道具で作ったものを置くクラウドの棚。

覚えるべき10の用語（すべて身近な例えつき）

#用語意味身近な例え
1リポジトリ（Repository）1つのプロジェクトのコードと変更履歴をまとめて保管する場所1冊のノートブック。プロジェクトごとに1冊ずつ用意する
2クローン（Clone）GitHub上のリポジトリを、自分のパソコンに丸ごとコピーすること図書館の本を借りてきて、手元で読み書きできるようにする行為
3ブランチ（Branch）コードの「並行世界」。本流から枝分かれさせて、別の作業場所を作るノートのコピーを作り、コピー上で下書きする。清書が終わったら本物のノートに反映する
4コミット（Commit）変更を「確定して記録する」操作。メモ（コミットメッセージ）を添えるWordの「名前を付けて保存」＋「この保存で何を変えたか」のメモ書き
5ステージング（Staging / Add）変更したファイルの中から「次のコミットに含めるもの」を選ぶ操作引っ越しの荷造り。全部の荷物の中から「今回のトラックに積むもの」を選別する
6プッシュ（Push）自分のパソコン上のコミットをGitHubにアップロードすること手元で完成した書類を、共有フォルダ（GitHub）に提出する
7プル（Pull）GitHubの最新の変更を自分のパソコンにダウンロードすること共有フォルダから、他の人が更新した最新版を手元にダウンロードする
8プルリクエスト（Pull Request / PR）「自分の変更を本流に取り込んでほしい」とチームに申請すること「この修正内容を確認して、問題なければ本番に反映してください」という稟議書
9マージ（Merge）ブランチの変更を本流に統合する操作。PRが承認された後に行う下書き（ブランチ）の内容を、正式な報告書（main）に転記・統合すること
10コンフリクト（Conflict）2人が同じ箇所を別々に変更した結果、Gitが自動で統合できない状態2人が同じ報告書の同じ段落を別々に書き換えてしまい、「どちらを採用するか」人間が判断する必要がある状態

コードがGitHubに届くまでの流れ（全体像）

自分のパソコン（ローカル）
ここで実際にコードを書く

ファイルを変更する
↓ git add ステージング（荷造り）
↓ git commit コミット（確定保存＋メモ）
↓ git push プッシュ（GitHubにアップロード）
↓
GitHub（リモート）
チーム全員がアクセスできるクラウド上の保管場所
郵便に例えると：コードの変更は「手紙」。git addは「手紙を封筒に入れる」。git commitは「封筒に宛名と内容メモを書いて封をする」。git pushは「郵便ポストに投函する（GitHubに届く）」。逆にgit pullは「自分宛ての郵便物を受け取る（GitHubから最新を取得する）」。

各ブランチは独立しているので、互いの作業が干渉しない。完成したブランチだけがmainに統合される。

日常の操作フロー完全ガイド

前提：初回セットアップ（1回だけ）

Gitを使い始める前に、自分の名前とメールアドレスを登録する。これは「変更の記録に自分の名前が表示される」ための設定であり、全コミットに自動で付与される。

# 自分の名前を登録（コミット履歴に表示される） git config --global user.name "田中太郎" # メールアドレスを登録（GitHubアカウントと同じものを推奨） git config --global user.email "tanaka@kurokawa-co.jp" # 設定を確認 git config --list

操作1：リポジトリをクローンする（初回のみ）

GitHubにあるプロジェクトを自分のパソコンにダウンロードする最初の操作。1つのプロジェクトにつき1回だけ行う。

# GitHub上のリポジトリを自分のPCにコピー git clone https://github.com/kurokawa-co/my-project.git # コピーされたフォルダに移動 cd my-project
図書館に例えると：図書館（GitHub）から本（リポジトリ）を借りてきて、自分の机（パソコン）に置く。以降はこの本の上で作業する。

操作2：ブランチを作成して切り替える

作業を始める前に、必ず新しいブランチを作成する。mainブランチ（本番）で直接作業してはいけない。

# 今いるブランチを確認（* がついているのが現在のブランチ） git branch # 出力例: # * main # develop # 新しいブランチを作成して、同時にそのブランチに切り替え git checkout -b feature/add-login-page # 確認すると、新しいブランチに切り替わっている git branch # 出力例: # main # develop # * feature/add-login-page

ブランチ名のルール

ブランチ名は「種類/内容」の形式で統一する。
feature/add-login-page（新機能の追加）
fix/payment-error（バグの修正）
hotfix/security-patch（緊急のセキュリティ修正）
日本語やスペースは使わず、英語の小文字とハイフンで書く。

操作3：コードを変更し、ステージング → コミットする

ファイルを編集した後、その変更を「記録」する操作。add → commit の2ステップで行う。

# どのファイルが変更されたか確認 git status # 出力例: # modified: src/pages/login.js ← 変更されたファイル # new file: src/pages/signup.js ← 新しく追加したファイル # 方法A：変更されたファイルを1つずつステージング（荷造り） git add src/pages/login.js git add src/pages/signup.js # 方法B：変更された全ファイルをまとめてステージング git add . # コミット（確定保存）。-m の後に「何を変更したか」をメモとして書く git commit -m "ログインページのUIを作成し、新規登録ページを追加"

良いコミットメッセージの書き方

コミットメッセージは「3ヶ月後の自分が読んでも何をしたかわかる」レベルで書く。

悪い例："修正" "fix" "update" ← 何を修正/更新したのか不明
良い例："ログインフォームのバリデーションエラーメッセージを日本語化"
良い例："決済APIのタイムアウトを30秒から60秒に変更（大量注文時の失敗を防止）"

操作4：プッシュする（GitHubにアップロード）

# 自分のブランチの変更をGitHubにアップロード git push origin feature/add-login-page # 初回プッシュ時は -u オプションを付けると、次回以降 git push だけで済む git push -u origin feature/add-login-page

この操作により、自分のパソコン上の変更がGitHubに反映される。他のチームメンバーがGitHub上で変更内容を確認できるようになる。

操作5：プルリクエスト（PR）を作成する

プッシュ後、GitHub上で「プルリクエスト」を作成する。これは「自分の変更を本流に取り込んでください」というチームへの申請書だ。

手順操作補足
1GitHubのリポジトリページを開くブラウザでアクセス
2黄色いバナー「Compare & pull request」ボタンをクリックプッシュ直後に自動表示される
3タイトルと説明を入力何を変更したか、なぜ変更したか、テスト方法を書く
4レビュアー（確認者）を指定右側の「Reviewers」からチームメンバーを選択
5「Create pull request」ボタンをクリックこれでレビュアーに通知が届く

良いプルリクエストの書き方

タイトル：何をしたかが一目でわかるように。「ログインページのUIを作成」など。
説明に含めるべき内容：
・変更の背景（なぜこの変更が必要か）
・変更の内容（何をどう変えたか）
・テスト方法（この変更が正しく動くことをどう確認したか）
・スクリーンショット（UIの変更がある場合）
・関連するタスクやチケットのリンク

操作6：レビューを受けてマージする

手順誰が操作
1レビュアーPRの「Files changed」タブでコードの変更内容を確認
2レビュアー問題がある箇所にコメントを残す（行番号の横の「+」ボタン）
3作成者コメントに基づいてコードを修正し、再度プッシュ（PRに自動反映される）
4レビュアー問題なければ「Approve」（承認）を選択して「Submit review」をクリック
5作成者 or レビュアー「Merge pull request」→「Confirm merge」で本流に統合
6作成者マージ後、不要になったブランチを「Delete branch」ボタンで削除

操作7：他の人の変更を取り込む（プル）

他のチームメンバーがmainブランチに変更をマージした場合、自分のパソコンにはまだ反映されていない。プルで最新を取得する。

# mainブランチに切り替え git checkout main # GitHubの最新をダウンロード git pull origin main # 自分の作業ブランチに戻る git checkout feature/my-task # mainの最新をブランチに取り込む（推奨） git merge main

作業前に必ずプルする

毎朝の作業開始前にgit pull origin mainを実行する習慣をつける。古い状態のmainから作業を始めると、後でコンフリクト（変更の衝突）が発生する確率が高くなる。「出社したらまずメールチェック」と同じ感覚で「作業前にまずgit pull」を習慣化する。

日常の操作フローまとめ

git pull origin main 最新を取得
↓ git checkout -b feature/xxx ブランチ作成
↓ コードを編集する
↓ git add . ステージング
↓ git commit -m "メッセージ" コミット
↓ git push origin feature/xxx GitHubにアップロード
↓ GitHub上でプルリクエストを作成
↓ レビューを受けて修正 → 承認 → マージ
↓ ブランチを削除して完了

GitHub Desktop（GUI版）という選択肢

上記のコマンドラインに抵抗がある場合は、GitHub Desktopという公式のアプリケーションを使うことで、ボタン操作だけでGit操作を行える。

コマンドGitHub Desktopでの操作

どちらを使うべきか

最初はGitHub Desktopから始めて、操作に慣れてきたらコマンドラインに移行するのが推奨。GitHub Desktopは視覚的にわかりやすいが、複雑な操作（コンフリクト解決、履歴の書き換え等）はコマンドラインの方が柔軟に対応できる。

よくあるトラブルと対処法

トラブル1：「変更がコンフリクトしています」

2人が同じファイルの同じ箇所を変更した場合、Gitは自動でマージできず「コンフリクト」を報告する。

# マージしようとするとコンフリクトが発生 git merge main # CONFLICT (content): Merge conflict in src/pages/login.js # Automatic merge failed; fix conflicts and then commit the result.

コンフリクトが発生したファイルを開くと、以下のような表示になっている。

<<<<<<< HEAD (自分の変更) const timeout = 60; ======= const timeout = 30; >>>>>>> main (他の人の変更)
手順操作
1<<<<<<< と >>>>>>> の間から、正しい方を残す（または両方を統合して書き直す）
2<<<<<<<、=======、>>>>>>> の行を全て削除する
3git add . で解決済みファイルをステージング
4git commit -m "コンフリクトを解決" でコミット
報告書の修正に例えると：「Aさんは数値を60に修正し、Bさんは30に修正した。どちらが正しいか確認して、最終版を確定させる」作業。2人に確認を取り、正しい値を決めてファイルを保存する。

トラブル2：「間違えてmainブランチで作業してしまった」

mainブランチで直接作業してしまった場合、コミット前であれば簡単に復旧できる。

# まだコミットしていない場合：変更を一時退避（stash）する git stash # 新しいブランチを作成して切り替え git checkout -b feature/my-task # 退避した変更を復元 git stash pop # あとは通常通り add → commit → push

トラブル3：「コミットメッセージを間違えた」

# 直前のコミットメッセージを修正（まだプッシュしていない場合） git commit --amend -m "正しいコミットメッセージ" # 注意：すでにプッシュ済みの場合は --amend を使うと履歴が食い違う。 # プッシュ済みなら新しいコミットで修正内容を追加する方が安全。

トラブル4：「プッシュが拒否された」

他の人がGitHub上で変更をプッシュした後、自分がプッシュしようとすると拒否される場合がある。

# エラー例： # ! [rejected] feature/xxx -> feature/xxx (fetch first) # hint: Updates were rejected because the remote contains work that you do not have locally. # 対処法：まずリモートの変更を取り込んでから再度プッシュ git pull origin feature/xxx # （コンフリクトがあれば解決する） git push origin feature/xxx

トラブル5：「ファイルを間違えてaddしてしまった」

# ステージングに追加したファイルを取り消す（ファイルの変更自体は残る） git reset HEAD src/pages/secret-file.js # 全てのステージングを取り消す git reset HEAD

トラブル6：「変更を全部取り消して元に戻したい」

# 特定ファイルの変更を取り消す（最後のコミット時点に戻す） git checkout -- src/pages/login.js # 【危険】全ファイルの変更を取り消す（元に戻せない！） git checkout -- .

git checkout -- . は取り消せない

この操作は未コミットの変更を全て破棄する。一度実行すると元に戻せないため、実行前に本当に不要か確認すること。不安な場合は先にgit stashで一時退避しておくと安全。

セキュリティの3層構造

Firebase APIキーの重要な性質

Firebase APIキーは「公開前提」で設計されている

「APIキーがコードに書かれている＝危険」と感じるが、FirebaseのAPIキーはプロジェクトの「住所」のようなもの。それ自体に読み書き権限はない。セキュリティはSecurity RulesとApp Checkで担保する設計。

ただし、アプリケーション制限（ドメイン/アプリ署名の制限）は必須。そしてサービスアカウントキー（管理者権限の鍵）は全く別物で、絶対に公開禁止。

08

社内コード管理の全体設計

なぜコード管理のルールが必要か

建設現場に例えると：設計図（コード）を誰でも自由に書き換えられる建設現場を想像してほしい。Aさんが壁を追加し、Bさんが知らずに同じ場所に窓を設計し、Cさんがその壁ごと削除する。完成した建物は当然ながら欠陥だらけになる。コード管理のルールとは、「設計変更は必ず全員に共有し、責任者の承認を経てから反映する」という、建設現場では当たり前のプロセスをソフトウェア開発に適用することである。

ブランチ戦略：コードの「並行世界」を管理する

ブランチとは、コードの「並行世界」のこと。本番用のコードから枝分かれさせて、別の世界で自由に作業し、完成したら本番に統合（マージ）する。以下が推奨されるブランチ構成だ。

ブランチ名役割誰が触れるか保護設定
main（本番）実際にユーザーが利用しているサービスのコード。常に動作する状態を維持直接の変更は禁止。プルリクエスト経由のみ最高レベルの保護 レビュー1名以上必須、CI通過必須
develop（開発）次のリリースに向けた開発中のコード。機能ブランチの統合先開発者がプルリクエストで統合中レベルの保護 レビュー推奨
feature/xxx（機能）個別の機能追加やバグ修正の作業場所。1つの機能＝1つのブランチ担当開発者が自由に作業保護なし（自由に作業可能）
hotfix/xxx（緊急修正）本番で発生した緊急バグの修正専用指名された開発者レビュー必須だが迅速対応
出版社に例えると：mainは「書店に並んでいる出版済みの本」。developは「次の版の編集中原稿」。featureは「各ライターが書いている原稿の下書き」。hotfixは「出版済みの本で見つかった誤字を緊急で正誤表を出す作業」。書店の本を直接書き換える人はいない。必ず編集プロセスを経て、次の版として出版する。

コードの変更が本番に届くまでの流れ

開発者がコードを変更
↓ feature/xxx ブランチにコミット（保存）
↓ プルリクエストを作成（変更申請）
↓ CI/CD が自動でテスト・検査を実行
テストが通らなければマージ不可
↓ レビュアー（別の開発者）がコードを確認・承認
問題があれば差し戻し、修正後に再レビュー
↓ develop ブランチにマージ（統合）
↓ ステージング環境で最終確認
↓ main ブランチにマージ → 本番に自動デプロイ

プルリクエストのルール

ルール設定内容理由
最低1名のレビュー承認mainブランチへのマージには最低1名の承認を必須化一人で全てを判断するミスを防止。「二人の目」の原則
CI/CDの全テスト通過自動テストが全て合格しないとマージボタンが押せない壊れたコードが本番に入ることを物理的に防止
自分のプルリクエストは自分で承認できない作成者と承認者は別人であることを強制チェック機能の形骸化を防止
承認後に変更があったら再承認承認後にコードが変更されたら承認がリセットされる承認後にこっそり変更を加える行為を防止
管理者もルールに従うAdminロールでもブランチ保護を回避できない設定権限者の「例外」がルールの穴になることを防止

CI/CD（自動テスト・デプロイ）で何をチェックするか

チェック項目非エンジニア向け説明ツール例
単体テストコードの各部品が正しく動くかを自動で検査。1000個の部品を人間が手動で検査するのは不可能だが、プログラムなら数分で完了Jest, pytest
リンター（コード規約チェック）コードの「書き方のルール」に従っているかを検査。全員が同じスタイルで書くことで読みやすさと保守性が向上ESLint, Prettier
セキュリティスキャン使用している外部ライブラリに既知の脆弱性がないかを自動検査。「この材料にリコール品が混ざっていないか」のチェックDependabot, Snyk
シークレット検出コード内にパスワードやAPIキーが混ざっていないかを検査。「封筒に個人情報が入っていないか」のチェックSecret Protection, git-secrets
ビルド確認コードが正しくコンパイル（完成品に変換）できるかの確認。「設計図通りに組み立てられるか」の検証GitHub Actions

秘密情報を守る3つのルール

ルール1：.gitignoreで秘密ファイルをGitHubから除外する

.gitignoreとは「このファイルはGitHubにアップロードしないで」というルールを書いた設定ファイル。プロジェクトの最初に必ず設定する。

# .gitignore の設定例 # 環境変数ファイル（パスワード等が入っている） .env .env.local .env.production # サービスアカウントキー *-service-account.json firebase-adminsdk-*.json # SSH秘密鍵 *.pem id_rsa

ルール2：環境変数で秘密情報をコードの外に出す

環境変数とは、コードの外にある「メモ書き」。コード自体にはパスワードを書かず、実行時に外部から渡す仕組み。

危険：コードに直書き

const API_KEY = "sk-abc123xyz";
const DB_PASS = "mypassword";

vs

安全：環境変数から取得

const API_KEY = process.env.API_KEY;
const DB_PASS = process.env.DB_PASS;

ルール3：GitHub Actionsのシークレット機能を使う

CI/CD（自動テスト・デプロイ）で秘密情報が必要な場合、GitHubの「Repository Secrets」機能を使う。管理者が画面上で秘密情報を登録すると、CI/CDの実行時に自動で環境変数として渡される。コードやログには表示されない。

絶対にやってはいけないこと

コード内にパスワードやAPIキーを直接記述してGitHubにプッシュすること。一度GitHubにアップロードされた秘密情報は、後から削除してもGitの履歴に残り続ける。「ファイルを消した」だけでは不十分で、Git履歴の書き換え（git filter-branch等）が必要になり、極めて手間がかかる。最初から混入させないことが最重要。

Google Cloud Secret Manager（本格運用向け）

Firebase Blazeプランを使用しているなら、Google Cloud Secret Managerが利用可能。秘密情報を暗号化して保管し、必要なサービスだけがアクセスできるよう権限制御する。サービスアカウントキーのファイルを持ち回る運用をやめ、Secret Manager経由で動的に取得する形に移行することが推奨される。

なぜ環境を分けるのか

飲食店に例えると：「試作キッチン（開発）」「味見テスト（ステージング）」「お客様に出す厨房（本番）」を物理的に分けること。1つのキッチンで試作と提供を兼用すると「試作品をうっかり客席に出す」事故が起きる。

本番へのデプロイは手動でやらない

本番環境へのデプロイ（コードの反映）は、開発者が手動でコマンドを叩くのではなく、CI/CD（GitHub Actions等）からの自動デプロイのみに限定するのがベストプラクティス。手動デプロイは「どのコードがいつ反映されたか」の追跡が困難であり、誤操作のリスクも高い。GitHub上でmainブランチにマージされたら自動的にFirebaseにデプロイされる仕組みを構築する。

よくある失敗パターンと防止策

失敗1：フリーランスにOwner権限を渡した

状況：「作業しやすいように」とOrganizationのOwner権限を外注先に渡した。

結果：契約終了後もOwner権限が6ヶ月間放置。他案件の全コードにアクセス可能だった。

防止策：Outside Collaborator（特定リポジトリ・Write上限）で招待。契約終了日に削除リマインダー設定。

失敗2：Security Rulesが「全開」のまま本番運用

状況：開発初期の「全データ読み書き許可」をそのまま本番に移行。

結果：第三者が全ユーザーの個人情報を取得可能な状態が3ヶ月放置。

防止策：「認証済み＋自分のデータのみ」まで絞る。本番デプロイ前のRules監査必須化。コンソールの警告放置禁止。

失敗3：サービスアカウントキーをGitHubにプッシュ

状況：管理者権限のキーファイルをそのままコードに含めてGitHubに送信。

結果：リポジトリが一時的にPublic設定の期間にボットがキーを検出。不正利用で数万円の請求。

防止策：キーはコードに含めず環境変数 or Secret Managerで管理。.gitignoreに登録。Secret Protection導入。

失敗4：予算アラートの通知先が退職者のまま

状況：アラート設定済みだが、通知先が退職者のメールアドレスのまま。

結果：バズでアクセス100倍。月末に15万円の超過に気づいた。

防止策：通知先を複数名のメーリングリストに設定。自動停止スクリプト構築。

失敗5：手動で本番にデプロイして事故

状況：開発者が「急ぎだから」と手動でfirebase deploy --only hostingを本番環境に実行。

結果：テスト未実施のコードが本番に反映され、表示が壊れた状態で2時間公開された。

防止策：本番デプロイはCI/CD経由のみに限定。手動デプロイ権限を持つ人を最小限にするか、本番プロジェクトのfirebase deploy権限を制限する。

SaaS・クラウドツール選定の7つの基準

GitHub・Firebaseに限らず、社内で新しいSaaSやクラウドツールを導入する際に必ず確認すべき7つの基準がある。ツールの「機能」だけを見て導入すると、後になってセキュリティ・コスト・移行の壁にぶつかる。導入前にこの7項目を確認することで、数ヶ月後の後悔を防げる。

#基準確認すべきこと身近な例え
1 セキュリティとアクセス制御 SSO連携が可能か。ロールベースの権限管理があるか。二要素認証を強制できるか。監査ログが取得できるか。SOC 2等の認証を取得しているか 「このビルには入館管理システムがあるか。フロアごとの鍵が分かれているか。来客の入退記録は残るか」
2 無料プランの罠 無料枠の上限を超えた時に何が起きるか（停止か自動課金か）。無料プロジェクトが非アクティブ時に一時停止されないか。商用利用が許可されているか 「無料お試し期間が終わったら、自動で有料に切り替わるのか、サービスが止まるのか」
3 従量課金の上限設定 予算上限（ハードキャップ）を設定できるか。予算アラートだけか自動停止もできるか。過去にユーザーから「高額請求」の報告がないか 「携帯電話の料金に上限を設定できるか。通知だけか、本当に止まるか」
4 データの所在と法的管轄 データがどの国・地域のサーバーに保管されるか。日本リージョンが選べるか。GDPRやデータローカライゼーション法への対応状況 「大事な書類を預ける倉庫がどの国にあるか。その国の法律で書類が差し押さえられるリスクがないか」
5 データポータビリティ（脱出可能性） データをエクスポートできるか。標準的な形式（CSV、JSON、SQL等）で出力可能か。別のサービスへの移行が技術的に可能か。ベンダーロックインの度合い 「この賃貸マンションを出る時、家具を持ち出せるか。それとも据え付けで持ち出せないか」
6 サポートとSLA 有料サポートの有無と応答時間。SLA（サービス稼働保証）のパーセンテージ。日本語サポートの有無。障害時の情報公開の透明性 「何か問題が起きた時、電話すれば何時間以内に対応してくれるか。そもそも日本語で対応してもらえるか」
7 オープンソースかプロプライエタリか ソースコードが公開されているか。セルフホスト（自社サーバーで運用）が可能か。ベンダーが倒産した場合にサービスを継続できるか 「お店が閉店しても、レシピが公開されていれば自分で料理を作り続けられるか。それとも、お店でしか食べられないメニューに依存しているか」

最も見落とされる基準：#5 データポータビリティ

多くの企業が導入時に機能と価格だけを比較し、「このサービスから出ていく時のコスト」を考慮しない。しかし、数年後に「もっと安いサービスが出た」「このサービスの方針が変わった」「買収されて値上げされた」といった事態は珍しくない。その時にデータを持ち出せないと、高くなった料金を払い続けるか、データを捨てて移行するかの二択を迫られる。導入前に「このサービスを辞める時、どうするか」を必ず確認する。

ツール導入時のセキュリティチェックリスト

新しいツールを社内に導入する際、最低限確認すべき項目を以下に整理する。

CHECK導入前に確認する10項目
  • サービスのSOC 2 / ISO 27001認証の取得状況を確認
  • データの保管リージョン（国・地域）を確認
  • SSO連携（SAML / OIDC）に対応しているか確認。非対応なら別途パスワード管理が必要になる
  • ロールベースのアクセス制御（RBAC）があるか確認。「全員が管理者」しかないサービスは危険
  • 監査ログ（誰がいつ何をしたか）が取得できるか確認
  • API経由でデータをエクスポートできるか確認
  • サービスの利用規約を確認。特に「入力データの学習利用」の有無。AIツールは特に注意
  • 従量課金の場合、予算上限またはアラートを設定できるか確認
  • 無料プランの制限事項（非アクティブ時の一時停止、商用利用制限）を確認
  • 過去のセキュリティインシデントの有無と対応を確認（Google検索で「サービス名 security breach」等）
不動産の内見に例えると：マンションを借りる前に「間取りが広い」だけでなく、「管理組合がしっかりしているか」「防犯カメラがあるか」「退去時の原状回復費用はいくらか」「管理会社が倒産したらどうなるか」を確認する。SaaS選定も同じ。機能（間取り）だけでなく、セキュリティ（防犯）・撤退コスト（退去費用）・運営の信頼性（管理組合）を総合的に評価する。

Supabaseを選ぶべきケース / Firebaseを選ぶべきケース

Supabaseが有利：チームにSQL経験者がいる。複雑なデータのリレーション（関連付け）が必要。ベンダーロックインを避けたい。将来的にセルフホストに移行する可能性がある。読み取り回数が多く、Firebaseの従量課金が高くつく場合。

Firebaseが有利：Google Cloudのエコシステム（BigQuery、Cloud Run等）を既に活用している。リアルタイム同期が中核機能（チャット、コラボレーションツール等）。NoSQLの柔軟なスキーマが適している。Google製品との統合が多い。

Supabase無料プランの最大の注意点

Supabaseの無料プランでは、7日間アクティビティがないプロジェクトは自動的に一時停止される。社内ツールのように利用頻度にムラがあるサービスの場合、連休明けにアクセスしたらプロジェクトが停止していた、という事態が起こりうる。本番サービスには必ず有料プラン（Pro $25/月〜）を使用する。
